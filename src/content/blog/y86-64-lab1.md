## 一上来写的是 x86，然后被 yas 骂了十几行

做 Y86-64 实验之前，我以为这只是"把一段 C 翻译成汇编"的机械活。真正动手才发现，这个实验的难点根本不在写代码，而在于**我得先忘掉 x86-64**。

第一次写 `sum.ys` 的时候，我几乎是凭着写 x86 的肌肉记忆敲下去的：`.text`、`.globl _start`、`movq`、`testq`。结果 `yas` 一口气报了十几行错，第一行就指着 `.text` 说 `Invalid line`，后面跟着一串 `Missing Colon`。

那一刻我才意识到：Y86-64 和 x86-64 长得像，但是**两套完全不同的规则**。这个实验真正想让我看清的，就是"指令集设计"这件事——它的每一条限制背后都有硬件代价的考量，而不是作者随手定的。

这篇就按我当时的顺序复盘一遍：先是我摸清的指令体系逻辑，然后是那个让我卡了很久的 bug，最后是几条我觉得值得记住的经验。

## 二、我把 Y86-64 的指令体系拆成了七条逻辑

写代码之前我先把 `sim/misc` 里的教材示例和 `.yo` 文件对着看了一遍。看完之后，我发现 Y86-64 的设计几乎每一条都在做同一个取舍：**牺牲表达能力，换取解码的简单**。下面是我梳理出来的七条。

### 1. 指令按功能分格式类，长度是变的

Y86-64 的指令长度不统一，但同一类指令长度固定。我实验里的两条指令正好覆盖了两种典型格式：

| 指令 | 机器码 | 长度 | 构成 |
|---|---|---|---|
| `call sum_list`（`sum.yo` 0x0014） | `80 50 00 00 00 00 00 00 00` | 9 字节 | 操作码 + 8 字节目标地址，**没有寄存器字节** |
| `rmmovq %rcx,(%rsi)`（`copy.yo` 0x007f） | `40 16 00 00 00 00 00 00 00 00` | 10 字节 | 操作码 + 寄存器字节 + 8 字节偏移量 |

规律在第一个字节里：**高 4 位是 icode（指令类别），低 4 位是 ifun（功能变体）**。`80` 说明这是 call 类，`40` 说明这是 rmmovq 类。解码器只要看高 4 位，就知道后面该按哪种格式继续读——`call` 不访问寄存器，所以它的格式里干脆没有寄存器字节。这就是"格式类"存在的全部意义。

### 2. 搬运动作被拆成了四条指令

x86-64 里一个 `movq` 靠操作数组合就能变通；Y86-64 直接按**数据流向**拆成四条独立的指令：

| 助记符 | 方向 | 我在实验里拿它干了什么 |
|---|---|---|
| `irmovq` | 立即数/符号 → 寄存器 | 装载地址（`irmovq ele1, %rdi`）和常量（`irmovq $8, %r8`） |
| `rrmovq` | 寄存器 → 寄存器 | 这次没用到 |
| `rmmovq` | 寄存器 → 内存 | 完成拷贝（`rmmovq %rcx,(%rsi)`，等价于 `*dest = val`） |
| `mrmovq` | 内存 → 寄存器 | 读链表结点（`mrmovq (%rdi),%rcx`，等价于 `ls->val`） |

把数据流向直接编码进操作码，解码器就不用去猜操作数是什么类型了。这是很典型的 RISC 式取舍。

### 3. OPq 只能寄存器对寄存器

`addq / subq / andq / xorq` 的操作数**必须都是寄存器**，没有例外。这条限制带来两个连锁反应：

想对内存里的数做运算，得先用 `mrmovq` 把它搬进寄存器；想加一个立即数，得先把常量 `irmovq` 进一个暂存寄存器。`copy.ys` 里指针自增就是这么写的：`irmovq $8,%r8` 然后再 `addq %r8,%rdi`。

好处是运算类指令的格式被压到了最短——**操作码加寄存器字节，一共两个字节**，不带任何内存或立即数字段，硬件解码的代价最小。

### 4. 没有 testq，判断为零要靠自己 AND 自己

Y86-64 没有 `testq`。但每条 OPq 执行时都会顺带更新 ZF/SF/OF，所以"判断一个值是不是零"的标准写法是让它和自己做 AND：

```
andq %rdi,%rdi      # 值不变，但刷新了 ZF
je done             # rdi 为 NULL（链表尾）就退出
```

`andq %rdi,%rdi` 不会改变 `%rdi` 的值，但它会重新计算标志位，于是 `je` 就有了可依据的条件码。条件码由前一条运算指令"顺带"产生，条件跳转只负责消费——**运算和控制流是解耦的**。

### 5. 寻址方式只有一种：D(rB)

所有内存访问一律写成"偏移量(基址寄存器)"，没有 x86 的 `(%rip)` 相对寻址，也没有变址寻址。放到链表上就很直观：

- `(%rdi)` 就是 `0(%rdi)`，即 `ls->val`（`val` 在结构体偏移 0 处）
- `8(%rdi)` 即 `ls->next`（`next` 在偏移 8 处）

地址计算硬件只需要一个加法器（基址加位移），而"取一个符号的地址"这件事交给 `irmovq 符号, %reg` 完成。

### 6. 没有运行时环境，栈得我自己划

伪指令这一层最能体现 Y86-64 的"裸"：

| 伪指令 | 作用 |
|---|---|
| `.pos 0` | 声明从哪个地址开始存放，保证 YIS 从 0 号地址取第一条指令 |
| `.align 8` | 8 字节对齐，和 `long` 的大小一致 |
| `.quad` | 分配 8 字节常量，符号引用在汇编期被解析成地址 |
| `.pos 0x200` + `Stack:` | 手工划出栈空间，再用 `irmovq Stack, %rsp` 初始化栈指针 |

没有 `.text`、没有 `.globl`、没有 `_start`。**栈要自己划，栈指针要自己设**，程序从 0 号地址开始一条条往下执行。平时写 C 时被编译器藏在背后的那些"运行时细节"，在这里全裸出来了——我觉得这是这个实验最值钱的部分。

### 7. 符号到机器码的映射，本质是汇编器做的两件事

这是我写在报告里的核心部分。以 `irmovq ele1, %rdi` 编码成 `30 f7 20 00 00 00 00 00 00 00` 为例：

| 字段 | 值 | 含义 |
|---|---|---|
| 操作码 | `30` | icode=3（irmovq），ifun=0 |
| 寄存器字节 | `f7` | rA=`F`（不用就补 F），rB=`7`（%rdi） |
| 常数字 | `20 00 ... 00` | 符号 `ele1` 的地址 0x20，小端序 |

三条规律：

1. **确定性映射**——助记符决定 icode，寄存器决定 4 位编号（%rax=0 一路到 %rdi=7，空位补 F），定长编码让解码变得机械。
2. **小端序**——多字节常数字低位字节在前。
3. **符号在汇编期就消失了**——`.yo` 文件里只有纯数字，符号指令只是给人看的视图。

所以所谓"符号指令与机器指令的对应关系"，拆开看就是汇编器干的两件事：**查表编码，再把符号表里的地址回填进去**。

## 三、两个程序跑通时的样子

这次要交两个程序，结构上共用一个模板：`.pos 0` 从地址 0 开始 → init 段设好堆栈并 `call` 函数 → 数据段 → 函数体 → `.pos 0x200` 预留栈空间。这个布局和教材里的 `asum.ys` 是一致的，两个程序都套它，出错面小了很多。

**`sum.ys`——迭代遍历链表，把每个结点的 `val` 累加。** 跑完 26 步，`Status 'HLT'`，`%rax = 0xcba`。这个值我提前算过：0xa + 0xb0 + 0xc00 = 3258，和程序输出对得上。

```
Stopped in 26 steps at PC = 0x1d.  Status 'HLT', CC Z=1 S=0 O=0
Changes to registers:
  %rax: 0x0000000000000cba   # 求和结果
  %rcx: 0x0000000000000c00   # 最后一次加载的结点值
  %rsp: 0x0000000000000200   # ret 弹栈后恢复
Changes to memory:
  0x01f8: 0x000000000000001d # call 压入的返回地址（halt 的位置）
```

**`copy.ys`——把 src 块复制到 dest，同时返回各元素的异或校验和。** 同样是 `Status 'HLT'`，`%rax = 0xcba`（这次是 0xa ^ 0xb0 ^ 0xc00），dest 的三个单元从 0x111/0x222/0x333 变成了 0xa/0xb0/0xc00。

两个程序都通过验证。但说实话，第一个版本远没有这么顺利——下面这段才是这次实验真正教我的东西。

## 四、四个坑，一个比一个隐蔽

### 坑 1：我把 x86 语法带进了 Y86-64

这个坑很蠢，但发生得很自然。报错长这样：

```
Error on line 16: Invalid line          ← .text
Error on line 22: Missing Colon         ← testq %rcx, %rcx
```

原因就是肌肉记忆：`movq`、`testq`、`.text`、`.globl`、`(%rip)` 这些在 Y86-64 里统统不存在。我后来整理了一张速查表贴在旁边，写的时候随时对照：

| x86-64 写法 | Y86-64 正确写法 |
|---|---|
| `movq mem, %reg` | `mrmovq D(%reg), %reg` |
| `movq %reg, mem` | `rmmovq %reg, D(%reg)` |
| `movq imm/sym, %reg` | `irmovq imm/sym, %reg`（数字带 `$`，符号不带） |
| `movq %reg, %reg` | `rrmovq %reg, %reg` |
| `addq mem, %reg` | 先 `mrmovq` 进寄存器，再 `addq %reg,%reg` |
| `testq %r,%r` | `andq %r,%r`，用 ZF 判零 |
| `addq $8, %reg` | 先 `irmovq $8,%r8`，再 `addq %r8,%reg` |
| `.text` `.globl` `_start` | 用 `.pos 0` 声明入口 |

顺便记一个排查手段：`cat -A 文件` 能看出隐藏字符，`^M` 就是 CRLF 换行——Windows 下编辑过的文件得转成 LF，否则 `yas` 会在你没意识到的地方报错。

### 坑 2：循环标号放错位置，程序读到内存垃圾后崩了

这是本次最深刻的一个 bug。

**现象**是这样的：

```
Stopped in 23 steps at PC = 0x5d.  Status 'ADR', CC Z=0 S=0 O=0
%rax: 0x020100ea   %rcx: 0x0200f430   %rdi: 0x20f7300000
```

**原因**是我把 `loop:` 这个标号写在了 `andq`/`je` 检查的**后面**。于是 `jmp loop` 直接跳回循环体，**整个 NULL 判断被绕过去了**。链表遍历完之后 `rdi` 已经变成 0，可是循环不退出，程序把地址 0 处的机器码当成数据读进来累加，再拿内存里的垃圾当指针用，第 5 次 `mrmovq` 访问非法地址，崩了。

最让我兴奋的是事后拆解那几个"垃圾值"——它们每一个都精确对应一条证据：

| 观察到的值 | 解码出来的事实 |
|---|---|
| `rcx = 0x0200f430` | mem[0] 的 8 个字节是 `30 f4 00 02 …`，也就是第一条指令 `irmovq 0x200,%rsp` 的机器码被当数据读了 |
| `rax = 0x020100ea` | = 0xcba（正确的前三次累加）+ 0x200f430（垃圾的第四项） |
| `rdi = 0x20f7300000` | mem[8] 的 8 字节，由第一条指令尾部加第二条指令开头拼出来的假指针 |
| 23 步、PC=0x5d、ADR | 第 5 次 `mrmovq (%rdi)` 拿着假指针访存，触发崩溃 |

修法很简单，把标号挪到检查**之前**，保证每次回跳都重新判断：

```
sum_list:
    xorq %rax,%rax
loop:                       # ← 标号必须在检查之前
    andq %rdi,%rdi          # 每一轮都重新判断
    je done
    mrmovq (%rdi),%rcx
    addq %rcx,%rax
    mrmovq 8(%rdi),%rdi
    jmp loop                # 跳回检查处
done:
    ret
```

**教训**：C 里的 `while (ls)` 每轮循环都会重新判断条件。翻译成汇编时，**循环回跳的那一跳必须落在条件判断指令上**。以前我从来没"看见"过这件事——它被编译器严格维护着，只有在手写汇编的时候才会暴露出来。

### 坑 3：改了源码，跑出来的还是旧结果

改完 `.ys` 直接跑 `yis`，结果还是老版本的行为。原因是 `yis` 执行的是上一次汇编生成的 `.yo`——我忘了重新 `yas`，或者上次 `yas` 失败留下了一个残缺的 `.yo`。

解决办法就是固定流程，每改一次源码就完整重跑一遍：

```bash
./yas sum.ys     # 有 error 必须处理，warning 可以忽略
./yis sum.yo
```

后来我又遇到 `Status 'ADR'` 但 `.yo` 看起来没问题的情况，第一反应就是 `ls -l` 对比一下 `.ys` 和 `.yo` 的修改时间，先把陈旧产物这个可能性排掉。

### 坑 4：报错很多，但真正的错只有一个

`yas` 的报错格式是 `Error on line N: 类型`，而且**一次最多只报 5 个**。一开始我盯着最后一条看，越看越糊涂。后来才明白：**第一个错误才是根源，后面的多半是连锁反应**。从那以后我只从行号最小那条开始查。

## 五、几条我想留下来的经验

1. **先分清两套指令集再动手写**。Y86-64 和 x86-64 长得像，规则完全不同：搬运四分法、OPq 不能访存、没有 testq、寻址只有 D(rB)。速查表放手边，比事后一行行排错快得多。
2. **循环的回跳点就是条件判断处**。C 的 `while` 语义是靠"检查 + 回跳"共同实现的，`jmp` 跳错位置就等于绕过了终止条件。这是本次最隐蔽、也最有教学价值的 bug。
3. **寄存器的值是排错的金矿**。崩溃时 `%rcx`、`%rdi` 里的垃圾值不是没意义的噪声，把十六进制按字节拆开，往往能反推出程序究竟读了哪块内存，从而精确定位出错的那一步。
4. **分清 error 和 warning**。`yas` 的 warning 手册里明说了可以忽略，error 必须清零；编译失败之后一定要重新生成 `.yo` 再运行。
5. **结构模板值得复用**。`.pos 0` → init（设栈 + call + halt）→ 数据段 → 函数 → `.pos 0x200 Stack:` 这套布局和教材 `asum.ys` 一致，两个程序共用，出错面小很多。
6. **先定验证标准再写代码**。sum 期望 `rax=0xcba`（加法），copy 期望 `rax=0xcba`（异或）并且 dest 内存要变。先把期望值算出来，跑完一眼就能判断对不对。
7. **`.yo` 是理解编码规则最好的教材**。它每一行都是"地址 + 机器码 + 符号指令回显"，符号到机器的映射一目了然，报告里的指令分析我直接从里面取材。

## 最后

这个实验真正让我改观的，不是"我会写 Y86-64 了"，而是我第一次清楚地看到**编译器平时替我挡掉了多少东西**。

栈是我划的，栈指针是我设的，循环的回跳位置是我决定的，返回地址是我靠 `call` 压进去的——write 错一个标号，程序就会去读指令的机器码当数据。以前写 C 的时候，这些都是"理所当然"；现在我知道它们每一条都需要有人去维护。
